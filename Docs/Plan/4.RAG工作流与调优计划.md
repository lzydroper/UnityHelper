# RAG 工作流与调优计划

## 一、目标

在 Dify 中完成可演示的 Unity 开发问答工作流，使产品能够根据用户问题精准调用对应知识库，并输出结构清晰、带来源依据、能辅助实际修改代码的回答。

当前落地版本为 `Workflows/1.1.0workflow.yml`。版本号采用 `大版本号.小版本号.迭代次数`：

- 大版本号：多个核心功能形成完整工作流时递增。
- 小版本号：新增或调整某个明确功能模块时递增。
- 迭代次数：同一功能的小修、小调参、小提示词迭代时递增。

## 三、Dify 工作流节点

| 节点 | 作用 | 关键配置 |
| --- | --- | --- |
| 开始节点 | 接收用户问题、代码片段、版本和语言上下文 | 输入变量：`query`、`code_context`、`unity_version`、`code_language` |
| 一级意图识别 | 判断主问题类型 | API 查询、报错调试、版本迁移、代码建议、概念解释、Lua/热更新、其他 |
| 二级错误类型识别 | 对报错调试请求进一步分类 | 空引用、生命周期、API 弃用、命名空间/包缺失、类型转换、IL2CPP/构建、Shader/材质、热更新绑定、其他 |
| 知识检索节点 | 按路由召回相关文档 | 官方文档库、Issues 案例库，使用混合检索 |
| Rerank 配置 | 对召回片段重排 | `qwen3-rerank`，每个检索节点保留 Top-5 |
| 答案生成节点 | 按不同意图生成结构化回答 | 引用文档、结合用户代码、输出修复建议 |
| Answer 节点 | 返回最终答案 | Markdown 输出，保留来源引用 |

## 四、失败处理策略

Dify 官方文档说明，LLM、HTTP、Code、Tool 节点支持内置错误处理；节点失败时可以选择默认中断、默认值兜底或失败分支。当前工作流优先处理最容易受免费额度影响的 LLM 生成节点：为 7 个答案生成节点配置 `error_strategy: default-value`，当模型调用失败时返回等待重试提示，而不是让整条 Chatflow 直接中断。

当前暂不启用自动重试，原因是 Gemini 免费额度下自动重试可能进一步增加短时间调用次数。若后续切换到更稳定的付费模型或备用模型，可再升级为 `fail-branch`，在失败分支里接备用模型或更详细的错误提示。

## 五、检索路由策略

| 用户意图 | 优先知识库 | 检索重点 | 回答重点 |
| --- | --- | --- | --- |
| API 查询 | `Unity_Official_Docs` | 类名、方法名、参数、示例 | API 用法、注意事项、示例代码 |
| 报错调试 | `Unity_Issues_Cases` + `Unity_Official_Docs` | 错误消息、堆栈、平台、相关 API | 错误类型、排查步骤、至少两种修复方案 |
| 版本迁移 | `Unity_Official_Docs` | Deprecated、Obsolete、Migration、Upgrade | 迁移结论、替代方案、风险说明 |
| 代码建议 | `Unity_Official_Docs` + `Unity_Issues_Cases` | 代码中的 API、类名、报错上下文 | 具体修改位置、修改后代码、验证建议 |
| 概念解释 | `Unity_Official_Docs` | Manual 概念章节、工作流说明 | 定义、使用场景、常见误区 |
| Lua/热更新 | `Unity_Lua_Hot_Update` + `Unity_Official_Docs` | Lua、xLua、toLua、绑定、热更新关键词 | 框架用法、绑定生成、热补丁与 Unity 侧适配要点 |
| 其他问题 | `Unity_Official_Docs` + `Unity_Issues_Cases` | 通用语义检索 | 明确资料不足时要求补充信息 |

## 六、版本字段策略

`unity_version` 保留为可选上下文字段，不作为强制检索过滤条件。

原因：当前官方文档库主要是 Unity 6.4，社区 Issues 案例不限定 Unity 版本，尚未形成 Unity 2022 LTS / Unity 6 的独立版本知识库。因此当前工作流会在回答中提示“当前官方知识库主要基于 Unity 6.4”，避免夸大版本切换能力。

后续如果创建独立版本知识库，可以将该字段升级为路由条件：

- `Unity_Official_Docs_2022_LTS`
- `Unity_Official_Docs_Unity6`
- `Unity_Migration_Cases`

## 七、Prompt 模板要点

所有答案生成节点遵循以下共同约束：

```text
请仅基于检索到的知识库内容和用户提供的代码回答。
如果资料不足，请说明缺少哪些信息，不要编造 API。
当用户提供代码时，必须指出具体修改位置。
参考来源必须来自检索资料中的标题或 URL。
```

不同分支的输出结构有所区分：

| 分支 | 输出结构 |
| --- | --- |
| API 查询 | 问题判断、API 用法或参数说明、注意事项、可参考代码、参考来源 |
| 报错诊断 | 错误类型判断、最可能原因、排查步骤、至少两种修复方案、可参考代码、参考来源 |
| 版本迁移 | 迁移结论、受影响 API 或功能、推荐替代方案、修改示例、风险与验证建议、参考来源 |
| 代码建议 | 代码问题判断、具体修改位置、修改后的参考代码、原因说明、测试建议、参考来源 |
| 概念解释 | 简明定义、工作原理或使用场景、常见误区、可参考做法、参考来源 |
| Lua/热更新 | 需求判断、适配要点、当前资料能确认的信息、风险与缺口、建议补充资料、参考来源 |

## 八、调优流程

1. 准备 20 个典型测试问题，覆盖 API、报错、版本迁移、代码建议、概念解释与 Lua/热更新。
2. 每次调整只改一个参数：Top-K、关键词/向量权重、Rerank、Prompt。
3. 记录每个问题的召回片段是否相关，以及最终回答是否引用来源。
4. 如果召回不准，先调知识库组合和检索权重。
5. 如果召回正确但回答泛化，再调 Prompt。
6. 使用 Gemini 免费额度测试时，每次 Dify Preview 提问之间主动间隔 20 到 30 秒，避免连续快速触发多次模型调用。
7. 最终保留一组稳定参数，写入测试记录和项目报告。

## 九、验收指标

| 指标 | 标准 |
| --- | --- |
| 典型问题数量 | 20 个 |
| 相关召回率 | 不低于 70% |
| 报错类型覆盖 | 至少 5 类，目标覆盖 8 类 |
| 答案可用性 | 80% 以上能直接理解或参考 |
| 来源引用 | 每次回答至少给出 1 到 3 个来源 |
| 响应速度 | 常规问答平均响应时间小于 30 秒 |
