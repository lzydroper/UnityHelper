# OpenWebUI 本地定制与后端网关计划

## 一、目标

在当前 OpenWebUI + Dify 接通方案的基础上，升级为可定制、可管控、可扩展的前后端架构：

1. 本地维护一份可构建的 OpenWebUI 源码，用于修改前端界面、品牌、默认交互和功能入口。
2. 新增项目自有后端网关，统一代理 OpenWebUI 到 Dify 的请求。
3. 将真实 Dify API 地址、API Key、调用策略和专属业务逻辑全部放在后端，避免暴露给浏览器。
4. 从服务端层面锁死模型入口，确保用户只能使用项目指定的 Unity RAG 助手。

## 二、总体架构

```text
用户浏览器
  ↓
自定义 OpenWebUI 前端
  ↓
项目自有 BackEnd 网关
  ↓
Dify OpenAI-compatible API 或 Dify 原生 API
```

前端负责体验和交互，后端负责安全边界、固定模型、业务规则、日志统计和 Dify 调用。

## 三、前端本地定制计划

1. 在 `FrontEnd` 中引入 OpenWebUI 源码：
   - 优先使用 fork 或 git submodule 固定上游版本。
   - 不建议直接散拷源码后失去上游版本记录。
2. 基于源码构建项目自定义 Docker 镜像。
3. 将 `OPEN_WEBUI_IMAGE` 从官方镜像切换为项目自定义镜像。
4. 前端定制范围：
   - 修改应用名称、欢迎语、默认页面和视觉品牌。
   - 隐藏或弱化不需要的设置入口。
   - 固定默认模型展示为 `unity-rag-assistant`。
   - 删除或限制普通用户切换外部供应商的路径。
   - 根据课程演示需要优化截图、历史记录和问答展示。
5. 注意：前端修改只能改善用户体验，不能作为安全边界。真正的接口锁定必须由后端实现。

## 四、后端网关计划

在 `BackEnd` 中新增轻量后端服务，建议使用 FastAPI 实现。

### 1. 对 OpenWebUI 暴露的接口

后端对外模拟 OpenAI-compatible API：

```text
GET  /v1/models
POST /v1/chat/completions
```

OpenWebUI 只连接项目后端：

```text
OPENAI_API_BASE_URL=http://backend:8000/v1
OPENAI_API_KEY=local-internal-key
```

### 2. 后端内部能力

1. 固定只允许调用项目指定的 Dify 应用。
2. 统一对外模型名为 `unity-rag-assistant`。
3. 将 Dify API Base URL 和 API Key 放在 `BackEnd/.env` 中。
4. 根据 Dify 接口能力选择内部调用方式：
   - 优先调用 Dify OpenAI-compatible 端点。
   - 如果插件能力不足，改为调用 Dify 原生 `/chat-messages` 或工作流接口。
5. 对响应内容做统一整理：
   - 保留 Markdown。
   - 保留代码块。
   - 规范来源引用格式。
   - 对 Dify 错误返回友好的前端提示。

### 3. 专属功能扩展

后端网关后续可逐步增加：

1. 请求日志：记录问题、用户、时间、耗时、状态码和错误信息。
2. 课程验收统计：统计 F1 到 F5 用例、10 轮连续对话结果。
3. 请求限流：避免演示或多人测试时误刷 Dify/API 额度。
4. 问题过滤：拦截明显无关、空问题或超长输入。
5. 系统提示词注入：统一要求回答 Unity 开发问题并输出来源。
6. 响应后处理：补充引用列表、统一中英文术语、规范代码建议格式。
7. 兼容层：未来替换 Dify 或新增备用模型时，OpenWebUI 前端无需大改。

## 五、Docker 编排调整

后续 `FrontEnd/docker-compose.yml` 建议升级为至少两个服务：

```text
open-webui
backend
```

OpenWebUI 环境变量建议固定：

```text
OPENAI_API_BASE_URL=http://backend:8000/v1
OPENAI_API_KEY=local-internal-key
ENABLE_DIRECT_CONNECTIONS=false
ENABLE_PERSISTENT_CONFIG=false
ENABLE_OPENAI_API=true
```

其中：

1. `ENABLE_DIRECT_CONNECTIONS=false`：禁止用户从浏览器直接添加外部模型供应商。
2. `ENABLE_PERSISTENT_CONFIG=false`：重启后强制回到 compose 与 `.env` 中的配置，防止 UI 设置覆盖部署配置。
3. `OPENAI_API_BASE_URL` 指向项目后端，而不是直接指向 Dify。

## 六、实施顺序

1. 在 `BackEnd` 中实现 OpenAI-compatible 网关最小版本。
2. 将当前 OpenWebUI 从直连 Dify 改为连接 `BackEnd`。
3. 使用 F1 到 F5 测试问题验证聊天链路。
4. 增加后端日志、错误处理和模型名锁定。
5. 引入 OpenWebUI 源码并构建自定义镜像。
6. 修改 OpenWebUI 前端品牌、默认页面和不需要的设置入口。
7. 完善 Docker Compose、README 和验收记录。

## 七、验收标准

1. OpenWebUI 页面已经体现项目自定义名称与界面调整。
2. OpenWebUI 中只显示 `unity-rag-assistant` 一个模型入口。
3. 浏览器端看不到真实 Dify API Key。
4. 所有聊天请求都先进入 `BackEnd` 网关。
5. 后端日志能记录请求问题、响应耗时、状态和错误信息。
6. Dify 连接由后端统一维护，前端不能随意切换到其他供应商。
7. `Docs/Plan/5.前后端接通与验收计划.md` 中 F1 到 F5 用例通过。
8. 连续 10 轮对话无明显断连或格式错误。

## 八、风险与注意事项

| 风险 | 说明 | 应对方式 |
| --- | --- | --- |
| OpenWebUI 上游更新频繁 | 深度修改源码后，后续升级成本会上升 | 使用 fork 或 submodule 固定版本，先小范围改 UI |
| 只改前端无法真正锁死接口 | 用户仍可能绕过浏览器请求后端接口 | 在自有后端中固定 Dify 地址和模型 |
| Dify OpenAI-compatible 插件能力有限 | 可能不支持 `/models` 或部分流式细节 | 后端自行实现 `/v1/models`，必要时转换 Dify 原生接口 |
| API Key 泄露风险 | 前端或浏览器中不能出现真实 Dify Key | Dify Key 只放在 `BackEnd/.env` |
| Docker 构建体积增加 | 本地构建 OpenWebUI 自定义镜像耗时更长 | 前期只使用官方镜像验证后端，后期再定制前端 |

## 九、阶段性结论

项目需要本地维护 OpenWebUI 源码来完成深度前端定制；同时也需要自有后端网关来实现真正的接口锁定和专属功能。第一阶段应优先完成后端网关，把安全边界和调用链路稳定下来；第二阶段再开始定制 OpenWebUI 前端界面。
